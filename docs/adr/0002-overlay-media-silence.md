# 拦截浮层期间终止媒体播放：模拟耳机暂停键，焦点仅作探测器

> v1.1（2026-10）修订：v1.0 的「持有音频焦点」方案实测对目标应用无暂停效果（焦点是
> 协作式 API，实测被拦应用并不让出播放），整体推翻。现行方案以 **模拟耳机媒体键**
> 为唯一执行手段：浮层可见期间由协调器经 [MediaSilencer] 在浮层每次变为可见时派发
> `KEYCODE_MEDIA_PAUSE`（`AudioManager.dispatchMediaKeyEvent`，按下+抬起，无需任何权限），
> 注册了媒体会话的主流播放器（ExoPlayer/短视频客户端）均响应暂停；音频焦点降级为
> **探测器**——浮层可见期间仍持有焦点，监听到焦点被应用抢走（= 有东西开始播放，
> 如对浮层按返回穿透刷出的新视频）即按 500ms 最小间隔补发暂停键并重新持焦。
> 触发覆盖所有拦截时刻：开屏选时、到期冷却、延时结束回落、额度用尽、黑名单禁止。

拦截浮层是 `FLAG_NOT_FOCUSABLE` 的悬浮窗，被拦应用仍在前台：开屏即播的短视频应用画面被浮层盖住、视频照放；且返回按键/手势穿透到被拦应用，刷出新视频继续播放——"没画面但有播放"。

## Considered Options

- **浮层改为可获焦窗口**：可拦截返回键穿透，但系统手势（回桌面）一并失效，违反防锁死底线，否决。
- **无障碍服务过滤返回键**（`canRequestFilterKeyEvents`）：仅覆盖按键事件，手势导航的返回不是按键，覆盖面随机型残缺，否决。
- **全局媒体流音量置零**：不依赖应用自觉，但误伤音量键与其它应用的媒体播放，恢复时机也难对齐，否决。
- **持有音频焦点（v1.0 选定，v1.1 废弃）**：协作式 API，实测对被拦应用无暂停效果；仅保留其"焦点被抢 = 有东西在播"的探测价值。
- **模拟耳机暂停键（v1.1 选定）**：程序化派发媒体键即等价耳机线控暂停，无需权限、主流播放器必然响应；副作用是浮层期间用户在其它应用刻意播放的音频也会被暂停（与焦点方案本来的副作用一致），个别不注册媒体会话的应用仍不响应（尽力而为）。

## Consequences

- 不注册媒体会话的应用可能不响应暂停键；如需覆盖，后续可按 `AudioPlaybackCallback` 检测到目标应用仍在播放时再做定向兜底。
- 浮层关闭后不主动恢复播放：已暂停的视频停在原地，由用户或应用自身策略决定。
- 常驻通知剩余时长的展示（轮询服务收集协调器 `notificationUsage` 流）与媒体终止无耦合：两种检测模式行为一致。
