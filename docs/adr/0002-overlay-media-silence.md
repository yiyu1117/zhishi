# 拦截浮层期间的媒体静音：持有音频焦点，而非让浮层可获焦或全局静音

拦截浮层是 `FLAG_NOT_FOCUSABLE` 的悬浮窗，被拦应用仍在前台：开屏即播的短视频应用（抖音等）画面被浮层盖住、声音照放；且返回按键/手势穿透到被拦应用，刷出新视频继续出声——"没画面但有声音"。选定方案：浮层可见期间由协调器经 [MediaSilencer] 请求并持有音频焦点（`AUDIOFOCUS_GAIN`），配合焦点协议的播放器立即暂停；被拦应用刷出新视频重新请求焦点时，焦点丢失监听立即夺回（最小间隔 500ms 防拉锯热循环），浮层隐藏即放弃焦点恢复常态。

## Considered Options

- **浮层改为可获焦窗口**：可拦截返回键穿透，但系统手势（回桌面）一并失效，违反防锁死底线，否决。
- **无障碍服务过滤返回键**（`canRequestFilterKeyEvents`）：仅覆盖按键事件，手势导航的返回不是按键，覆盖面随机型残缺，否决。
- **全局媒体流音量置零**：不依赖应用自觉，但误伤音量键与其它应用的媒体播放，恢复时机也难对齐，仅可作不遵守焦点协议应用的兜底（未实现）。
- **持有音频焦点（选定）**：协作式 API，主流媒体应用（ExoPlayer/短视频客户端）均遵守；实现小、无副作用。

## Consequences

- 不遵守音频焦点协议的应用在拦截期间仍可能出声；如需覆盖，后续可按 `AudioPlaybackCallback` 检测到目标应用仍出声时再做定向兜底。
- 常驻通知剩余时长的展示（轮询服务收集协调器 `notificationUsage` 流）与静音无耦合：无障碍模式没有应用自有的常驻通知，静音行为两种模式一致。
