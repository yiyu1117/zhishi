# 前台判定采用"前台机器集合"：可见即前台 + 退后台挂起确认

分屏/自由窗口中被管理应用未获焦时，系统只把焦点窗口当作前台：拦截浮层只在点进该窗口时弹出，用户在另一侧未管控应用上操作期间，被管理应用照常出声运行。同时，音量条等瞬态系统窗口在部分 ROM 上不属于已知瞬态包名，其窗口事件伪装成前台切换，直接派发退后台会误关拦截浮层（表现为"调音量拦截窗就消失"）。选定方案（无障碍模式）：

1. 服务开启 `flagRetrieveInteractiveWindows`（`canRetrieveWindowContent` 已开启；仅读窗口根节点的 packageName，不读任何内容），每个窗口状态事件汇总全部可见窗口的归属包名上报；
2. 协调器以"前台机器集合"取代单一前台：可见窗口中的被管理应用立即进入前台（弹浮层、计时），窗口消失即退后台——可见性是直接证据，无需确认；
3. 焦点切换路径的退后台走挂起确认：短候轮询 UsageStats，出现"新应用前台事件 + 原应用暂停记录"才证实切换；仅见新应用事件而原应用始终无暂停记录（被强杀/崩溃）的场景按安全窗（10 秒）强制放行；两者皆无（音量条等瞬态窗口没有使用统计记录）判为误报丢弃，浮层与计时如常。

## Considered Options

- **浮层可获焦 / 逐窗口浮层**：可挡住返回键穿透，但系统手势一并失效违反防锁死底线；逐窗口浮层需持续读取窗口几何并跟随，复杂且 ROM 差异大，否决。
- **把音量条包名加入瞬态过滤**：各 ROM 包名与形态不一（HyperOS 与 AOSP 不同），逐个适配治标不治本；挂起确认以"是否有使用统计记录"为判据，与具体包名无关。
- **用 UsageStats 判定可见性**：使用统计只有"前台活动"概念，未获焦的分屏窗格不产生可靠信号，无法覆盖本场景。

## Consequences

- 需重新启用一次无障碍服务（或重启手机）让新标志生效；标志未生效时退化为旧行为，挂起确认仍然有效。
- 最近任务等系统界面若被 ROM 报为应用窗口，理论上可能误判为"可见"；依赖全链路诊断日志（`ZhishiGuard`）定位。
- 轮询（兼容）模式没有窗口可见性信号源：分屏未获焦拦截不覆盖该模式；退后台挂起确认在轮询模式下同样生效（其事件本就来自 UsageStats，额外延迟约 0.5–1 秒）。
- 真实切换的退后台判定晚约 1–2 秒（等证据落账），会话/冷却时间误差可忽略；服务权限面扩大到"读取窗口根节点包名"，不存储、不上传任何窗口内容。
